Lead workflow orchestrator

Brightfield Solar is a fictional installer. Twelve lead rows go through a mock CRM, a mock calendar and a mock outbox. A ledger skips work that already finished, a failed booking is retried or handed to a named person, and a follow-up stays queued until someone approves that exact draft. What it handles:

  • Repeat leads: two exact copies and one copy that differs by letter case, spacing and phone punctuation become one CRM record per person.
  • Half-empty leads: a blank address, "TBD", "see attached", "about 900" or "n/a" opens one internal task. A later blank value does not wipe a real address or phone.
  • A calendar that drops calls: one lead fails twice and is then booked. One lead fails three times and is assigned to Priya Shah. Slots are not double-booked.
  • A person before anything is sent: the run opens the approval file read-only. The outbox gets a message only after approve, and only when the approved text still matches.

This demo is offline. CRM, calendar and mail are SQLite tables. The draft is a template, and the first line says so. No model is called. No account is connected.

How it was tested

  • 22 tests pass, 0 fail (Python 3.12.3, pytest 9.2.0, 1.73 seconds).
  • 12 inbox rows, 9 CRM records, 4 tasks, 8 events, 1 exception, 9 drafts, 0 emails. The tests count a second run as 0 new CRM writes, 0 new events and 0 new emails.
  • After the eight booked drafts are approved: 8 messages in the outbox, 1 draft still queued (the call that was never booked). The run after that adds 0 emails.
  • Crash and resume: stopping after ledger mark 4 leaves one event and no drafts. Continuing matches a clean run. The same check at marks 1, 7, 15, 30, 45 and past the end matches too.
  • One default run on this machine: 0.464 seconds, including the seeded 0.05s and 0.10s waits. With the waits set to zero: 0.126 seconds.

Honest caveats:

  • The company, the leads and the addresses are invented. There is no Salesforce, Gmail or Google Calendar behind the tables.
  • The two calendar failures are planted so the retry and the hand-off can be seen. They are not a live error rate. Passing --no-faults turns the plant off.
  • The approval file is local. The run cannot insert an approval. A person who can edit the file on disk can. The audit log stores the email address.
  • Slots are labels for Tuesday 10 Nov 2026, Pacific wall time. They are not checked against a real person's calendar.
  • A site address with no number, or shorter than 8 characters, is treated as missing. A real rural name in that shape would be flagged.
  • Tasks are rows in the file. They are not tickets in another system.
